# ADR-0007: Shared Schemas via Pydantic + OpenAPI

- **Status:** Accepted
- **Date:** 2026-05-15
- **SRS refs:** NFR-SEC-03, NFR-MAINT-03, NFR-PORT-03

## Context

Every inbound message must be validated against an expected schema (NFR-SEC-03). All public APIs must be documented with OpenAPI or comparable schema (NFR-MAINT-03). The protocol must be versioned and incompatible clients rejected (NFR-PORT-03).

The server is Python (ADR-0002); the web client is TypeScript. Two parallel type definitions invite drift — a wire-format bug that no test catches until production.

## Decision

**Pydantic v2 models in `packages/shared/`** are the single source of truth for all wire schemas. From them, we derive:

1. **Server-side validation** — FastAPI uses the models directly for REST and we use them explicitly for WebSocket frame validation.
2. **OpenAPI 3.1 spec** — FastAPI emits it for REST. WebSocket frame catalogue is generated by a small script that walks the Pydantic models and writes a JSON Schema bundle.
3. **TypeScript types for the client** — generated by `datamodel-code-generator` (Pydantic → JSON Schema → TS types via `openapi-typescript` and `json-schema-to-typescript`). The generated file is checked into `apps/web/src/net/generated.ts`. CI fails if it's out of date with the Pydantic source.

Every schema has a `schema_version: int`. Every wire envelope (`{v: int, type: str, payload: ...}`) carries the version explicitly.

## Consequences

### Positive
- Impossible (in practice) for the client and server to disagree about a wire format — drift is a CI failure.
- OpenAPI doc is always accurate (NFR-MAINT-03).
- New developers can read one place — `packages/shared/` — to understand the protocol.
- Versioning is built-in from day one (NFR-PORT-03).

### Negative / Trade-offs
- Adds a code-generation step to CI. Mitigated: the generator is deterministic and the artifact is committed (so PRs that change schemas show the type changes too).
- Pydantic v2 has a learning curve (especially for discriminated unions). Acceptable.

### Neutral
- If we later add a non-TS client (mobile native, CLI), it gets generated types from the same JSON Schema bundle.

## Alternatives Considered

### Option A — Hand-maintained TS types
**Rejected:** drift is a matter of when, not if.

### Option B — gRPC + protobuf
Cross-language by design. **Rejected:** browser support is awkward (gRPC-Web is a layer of indirection), JSON-over-WS is simpler and meets latency targets.

### Option C — JSON Schema authored directly, both sides codegen'd
**Rejected:** JSON Schema is verbose to write by hand; Pydantic gives us idiomatic Python ergonomics and emits JSON Schema for free.
